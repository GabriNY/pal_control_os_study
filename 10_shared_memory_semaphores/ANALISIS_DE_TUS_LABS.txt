4) 11_Semaphore.c -> versión revisada:
   00_labs_usuario_revisados/04_semaforo_exclusion_mutua_argumentos.c

P = semop(-1):
    si sem=1 -> pasa a 0 y entra.
    si sem=0 -> el proceso queda bloqueado.

V = semop(+1):
    libera el recurso y puede despertar a otro proceso bloqueado.

MUY IMPORTANTE SOBRE TUS ARCHIVOS ORIGINALES
---------------------------------------------

`11_semaphoreinit.c` usa key 0x4444.
`11_Semaphore.c` usa key 0x1111.

Por lo tanto NO están conectados al mismo conjunto de semáforos tal como fueron
subidos. Si el profesor pregunta por qué `./semaphore g ...` no encuentra el
semaforo creado por el inicializador, esta diferencia de KEY es la primera cosa
que debes revisar.

============================================================
COMO SE JUNTAN SHARED MEMORY + SEMAPHORE
============================================================

Sin semáforo:

Proceso B ----+
              +-----> contador en SHM
Proceso C ----+

Ambos pueden leer el mismo valor y pisarse.

Con semáforo:

Proceso B -> P() -> [contador en SHM] -> V()
Proceso C -> P() -> [contador en SHM] -> V()

Solo uno entra a la sección crítica por vez.

============================================================
POSIBLE CONTROL DE 5 PROCESOS
============================================================

A (padre/coordinador)
|-- B
|-- C
|-- D
`-- E

Total: 5 procesos.

A crea:
- SHM contador=0
- SEM valor=1

B,C,D,E:
- P()
- contador++
- V()

A:
- wait() x4
- muestra contador
- shmctl(IPC_RMID)
- semctl(IPC_RMID)

Este patrón está implementado en:
10_shared_memory_semaphores/05_shm_sem_cinco_procesos/
y como control en:
11_controles_shm_semaphore/control_03_shm_semaforo_cinco_procesos/
